# AI 市场监控工程规范

对本仓库进行任何工程变更时都遵循此 Skill。保持产品边界：系统只提供可追溯的决策辅助；除非用户明确启动独立范围，否则不得加入自动交易或交易所私有 API。

## 加载相关规范

规划或修改代码前：

1. 阅读 [references/architecture.md](references/architecture.md)，了解系统边界、已批准技术栈、包结构和数据流规则。
2. 阅读 [references/quality-gates.md](references/quality-gates.md)，确定 TDD 要求和验证矩阵。
3. 变更涉及信息源、资产、告警、延迟或产品范围时，阅读仓库 `README.md` 链接的相关产品文档。
4. 使用 `$repo-task-state` Skill 的 `preflight` 模式检查仓库当前状态，保留与任务无关的用户修改。
5. 创建开发分支、准备提交、创建 PR 或执行 Squash Merge 前，完整阅读并遵循 [Git 分支与提交规范](../../../docs/GIT_COMMIT_CONVENTION.md)。

不得静默替换已接受的技术方案。实施实质性偏离前，先在 `docs/DECISIONS.md` 记录原因和产品影响。

## 规划变更

每项实施任务都要：

1. 明确可观察行为和验收标准。
2. 确认负责该行为的业务模块。
3. 明确失败、重试、幂等、数据过期和审计要求。
4. 选择满足目标的最小改动。
5. 编辑前确定需要的测试和质量门禁。

保持领域规则独立于 Hyperliquid、PostgreSQL、Discord、来源特有载荷和模型供应商。在接口使用方定义接口。避免臆测性抽象、通用 `utils` 包和框架驱动的机械分层。

## 使用务实 TDD

以下行为使用 red-green-refactor：

- 领域规则和计算；
- 信息源解析和标准化；
- 去重和幂等；
- 实体、别名、金融工具和关系映射；
- 告警分类和质量门；
- 缺陷修复和回归行为；
- 重试、过期数据和降级行为。

修复缺陷前先编写能够复现问题的失败测试。无法合理从单元测试开始时，先建立最接近真实行为的自动化检查，例如 fixture、集成、迁移、契约或回放测试。不得为了声称采用 TDD 而添加无意义测试。

纯文档修改不要求运行代码测试。机械重构必须保持现有测试通过。依赖和配置变更必须通过构建以及相关集成或启动检查。

## 保持管道保证

按以下顺序实现可靠链路：

`发现 -> 快照 -> 标准化/去重 -> 事件抽取 -> 实体/资产映射 -> 关联行情上下文 -> 分析 -> 质量门 -> 投递`

每个异步边界都要：

- 持久化足够的安全重试状态；
- 使用稳定的幂等键；
- 假设任务至少执行一次；
- 记录时间戳和版本标识；
- 限制并发并实施背压；
- 区分确定性事实和模型推理。

让 Hyperliquid WebSocket 更新走内存快路径。不得把每个 tick 放入任务队列或永久存储。只持久化采样聚合、异常、stale 状态变化和事件窗口。通过官方实时元数据发现 `xyz` 金融工具，不得硬编码其可用状态。

使用 River 处理可靠任务，但在项目业务表中保存投递状态。将 River 任务视为至少执行一次，并保证 worker 幂等。

## 完成变更

运行 [references/quality-gates.md](references/quality-gates.md) 中所有适用门禁，并修复本次变更引起的失败。无法运行某项门禁时，报告具体命令、原因和剩余风险，不得描述为已完整验证。

行为、架构、Schema、运行要求、资产映射、告警语义或已接受决策发生变化时，在同一次变更中同步更新文档。

开发分支、提交标题、PR 标题和最终 Squash Merge 标题必须遵循 Git 分支与提交规范：分支使用与提交类型一致的前缀；`type` 和 `scope` 使用英文，描述和正文使用中文。TDD red 阶段的故意失败测试不得作为失败提交保留在 PR 中。

最终交付必须说明：

- 可观察行为发生了什么变化；
- 添加或修改了哪些测试；
- 实际运行了哪些门禁及其结果；
- 跳过了哪些门禁以及原因；
- 是否存在剩余风险；
- 下一步的具体任务、产物和完成条件。
