# TDD 与质量门禁

## 测试原则

使用务实 TDD。测试可观察行为和失败处理，不绑定私有实现细节。

添加或修改确定性行为时执行 red-green-refactor：

1. 编写能够证明需求或缺陷的最小失败测试。
2. 确认测试因预期原因失败。
3. 完成使测试通过的最小生产修改。
4. 在测试保持通过的前提下重构。

解析器和外部协议优先使用经过保存的一手 fixture、golden file、契约测试和回放测试。清除 fixture 中的密钥和不稳定字段。

SQL、事务、锁、迁移、River、`NUMERIC` 和 JSONB 行为必须使用真实 PostgreSQL 测试，不得用 mock 替代数据库语义。只有窄外部边界确实需要确定性本地替代时才使用 mock。

覆盖率是风险诊断工具，不是正确性证明。不得只用全局覆盖率阈值阻塞变更；当关键行为缺少有意义的正常、边界、失败或回归测试时必须阻塞。

## 测试层次

| 层次 | 必须覆盖的重点 |
|---|---|
| 单元测试 | 领域规则、计算、分类、映射、去重 |
| Fixture/golden | HTML、XML、JSON、多语言内容、Discord Embed 渲染 |
| 契约测试 | Hyperliquid 载荷、官方来源 Schema、模型结构化输出 |
| 集成测试 | PostgreSQL 查询、迁移、事务、River 任务 |
| 回放测试 | WebSocket 重连、重复事件、stale 数据、事件行情窗口 |
| 端到端 smoke | 从来源 fixture 到持久化告警和 Discord Webhook 假服务 |
| Fuzz | 解析器、解码器、标识符、畸形外部载荷 |

## 版本化与幂等写入测试矩阵

新增或修改带自然身份、幂等键、当前版本指针或不可变历史表的写入路径时，必须根据适用语义覆盖以下行为，不能只测试首次成功写入：

1. **精确重放**：相同幂等键和相同输入必须返回相同的 identity ID、version ID 与版本号，不得新增版本。
2. **逐字段冲突**：固定幂等键，逐个修改所有持久化结果字段，每一项都必须被识别为冲突。domain 字段、Schema 或 INSERT/UPDATE 字段变化时，必须同步核对并更新该表格测试。
3. **自然身份演进**：不同幂等键和相同自然键应按领域规则追加下一版本或明确拒绝；历史版本必须保持不可变。
4. **非法输入双路径**：格式、枚举、日期范围等非法输入必须同时覆盖首次写入和幂等键已存在的路径。错误必须反映真实输入问题，且不得产生数据库状态变化。
5. **并发矩阵**：至少覆盖相同自然键加相同幂等键、相同自然键加不同幂等键，以及涉及多个资源时的反向获取顺序，例如 `A -> B` 与 `B -> A`。测试必须设置超时，并断言无重复版本、裸唯一约束错误或死锁。
6. **时间语义**：`date` 按民用日期跨正负时区验证不移日；`timestamp` 按同一瞬时验证。不得用时间戳断言代替日期语义测试。
7. **迁移兼容**：涉及 Schema 时，从前一版本携带真实数据升级，验证历史回填、当前版本指针、失败回滚和适用的降级行为。

SQL、事务和锁相关项必须在真实 PostgreSQL 上验证。缺陷回归测试必须先在旧实现或等价故障注入下因预期原因失败；仅新增一个在修复前后都通过的测试，不构成回归证明。

代码评审时必须核对持久化字段集合与幂等比较字段集合一致。现有测试全绿或总体覆盖率提高，不能替代这项字段级审查。

## 开发门禁

每次代码修改后运行：

```bash
gofmt -w <changed-go-files>
go vet ./...
go test -count=1 ./...
go build ./...
```

在 red-green 过程中同时运行最聚焦的失败测试。完成变更时，不得只依赖缓存的测试结果。

修改 SQL 或 Schema 时同时运行：

```bash
sqlc generate
git diff --exit-code
```

生成文件更新后再次运行生成命令，工作区必须不再产生差异。

## 合并门禁

实现准备交付或合并前运行：

```bash
go test -race -count=1 ./...
go vet ./...
go build ./...
govulncheck ./...
```

### 真实外部链路

Issue 验收包含真实外部 API、真实凭据、真实数据、生产网络或真实通知投递时，必须在合并前取得脱敏的 live check 成功证据。fixture、mock、契约测试、默认 CI 和离线完整门禁不能替代该证据。live check 未通过或尚未执行时：

- 保持 Issue 和 PR 开放，不勾选对应验收项；
- 不得标记 `DONE`、合并、关闭 Issue或宣称完整接入；
- 需要用户输入凭据时停在合并前，提供安全命令并等待结果；
- 外部服务不可用时只报告离线完成范围和阻塞条件，不把 live check 降格为剩余风险。

只有任务在实施前已拆分为独立的“离线实现”Issue，且该 Issue 明确不承诺真实链路时，才允许在 feature flag 默认关闭的前提下先合并；真实启用与验收必须由后续独立 Issue 跟踪。

根据变更范围同时要求：

- 对受支持的真实 PostgreSQL 版本运行集成测试；
- 从空数据库运行全部迁移；
- 从前一个 Schema 版本执行升级迁移；
- 执行 Hyperliquid fixture 和断线重连回放；
- 执行信息源解析 fixture/golden 测试；
- 执行 Discord 重试、频道路由和幂等测试；
- 执行长期 worker 优雅关闭测试；
- 构建 Docker 镜像并完成启动 smoke test。
- 存在 `cmd/vertical-slice` 时运行 `./scripts/check-vertical-slice.sh`，验证来源 fixture 到 Discord 假服务的完整闭环及跨进程业务幂等。

在仓库工具或 CI 中固定工具版本，不得依赖开发机恰好安装的全局 linter。

## 文档门禁

纯文档变更需要：

- 验证链接和引用路径；
- 检查各文档决策是否冲突；
- 配置 Markdown 格式或链接检查后运行相应命令；
- Go module 尚未建立时，不运行无关的 Go 门禁。

## 失败处理

- 不得通过削弱或删除有效测试绕过失败。
- 未审查语义差异前不得更新 golden file。
- 必需门禁失败时不得宣称完成。
- 出现无关的既有失败时，尽可能证明其在本次变更前已存在并单独报告。
- 外部服务不可用时，运行全部离线门禁并报告未验证边界及剩余风险；若真实链路属于当前 Issue 验收，仍须阻塞合并。
