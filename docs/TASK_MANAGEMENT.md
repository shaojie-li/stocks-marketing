# 任务管理规范

状态：Active v1.0
更新日期：2026-08-15

## 1. 单一事实源

GitHub Issues 是实施任务的唯一事实源：

- Issue 保存目标、范围、验收标准、依赖、测试、质量门禁和完成记录。
- GitHub 的 Open/Closed 表示任务是否完成。
- `docs/TASKS.md` 只保存路线、稳定编号、依赖顺序和 Issue 索引，不复制 Issue 正文。
- 长期产品边界、架构和已接受决策保存在项目文档及 `docs/DECISIONS.md`。

## 2. 渐进建单

只为当前可执行任务、下一层直接依赖和必须提前验证的关键风险创建 Issue。远期想法先保留在路线文档中，范围和验收明确后再建单。

## 3. 标题与编号

计划任务使用：

```text
[M<里程碑>][T-<三位编号><可选大写子任务后缀>] <结果导向标题>
```

Bug、安全和运维任务分别使用 `[Bug]`、`[Security]`、`[Ops]`，不占用 `T-` 编号。稳定编号一旦分配不得复用；GitHub Issue 编号不能替代稳定编号。

## 4. 标签

| 标签 | 用途 |
|---|---|
| `status:next` | 当前唯一优先执行的 Issue |
| `status:blocked` | 缺少权限、凭据、外部决策或前置任务 |
| `type:design` | 产品边界、领域规则、架构或契约设计 |
| `type:feature` | 用户可观察的产品能力 |
| `type:infra` | 工程、数据库、CI、部署或可观测基础 |
| `type:bug` | 已存在行为不符合预期 |
| `risk:security` | 安全、凭据或交易权限风险 |
| `risk:data-correctness` | 行情、时间窗口、映射、幂等或审计正确性风险 |

同一时间只能有一个开放 Issue 使用 `status:next`。`status:blocked` 必须在正文写明阻塞和解除条件。模块、优先级和里程碑不额外创建标签。

## 5. 里程碑

| 里程碑 | 完成条件 |
|---|---|
| `M0 规则与数据可行性` | 全局分析规则、输出契约和核心数据源能力得到验证 |
| `M1 可执行工程基线` | Go、PostgreSQL、可靠任务和最小垂直链路可运行 |
| `M2 全局分析闭环` | 多市场数据、确定性指标、AI 分析和 Discord 投递闭环完成 |
| `M3 分阶段报告` | 开盘、收盘、隔夜、周末和周一预期报告可配置运行 |
| `M4 影子运行验证` | 数据质量、报告价值、运行可靠性和风险边界得到持续验证 |

## 6. Issue 必填内容

每个工程 Issue 必须包含：

1. 目标和用户价值；
2. 依赖及解除条件；
3. 范围与非目标；
4. 可观察行为与验收标准；
5. 测试与质量门禁；
6. 失败、重试、幂等、过期数据、安全和审计要求；
7. 完成记录，包括实际验证、剩余风险和下一任务。

## 7. 状态流转

```text
任务索引
→ 创建 Open Issue
→ 依赖满足
→ 唯一 status:next
→ 实施与验证
→ 补充完成记录
→ Closed
```

创建 Issue 不代表开始实施，也不自动创建分支、提交、PR、部署或生产写操作。

## 8. 完成定义

任务只有在可观察验收标准满足、适用测试与质量门禁通过、文档同步、外部真实链路验收完成且剩余风险已记录后才能关闭。无法执行的门禁必须说明原因，不能视为已通过。
